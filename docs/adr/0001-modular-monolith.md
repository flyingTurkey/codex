# ADR-0001：采用模块化单体作为首期后端架构

- 状态：Accepted
- 日期：2026-07-13
- 范围：Round 00 及首期数字化情报、安全情报

## 背景

首期需要建立统一来源接入、证据留存、内容处理、审核和发布门禁，但当前还没有需要独立扩缩容或独立发布的业务模块。过早引入微服务会放大分布式事务、契约演进、观测与部署成本。

## 决策

采用 FastAPI 模块化单体：API 与 Celery Worker 复用业务服务和 `packages/contracts` 契约，PostgreSQL 是业务事实唯一权威存储，Redis 只承担缓存、锁和队列，对象存储保存原始证据。

后续业务模块必须满足：

- 模块拥有自己的应用服务、领域规则和持久化边界；
- 不允许直接访问其他模块的 ORM 表，只能通过公开服务或契约协作；
- 外部来源统一实现 `SourceAdapter`，原始响应先保存再解析；
- 公开 API 统一位于 `/api/v1`，错误采用 Problem Details；
- 数据库变更只通过 Alembic，生产环境不使用 ORM 自动建表；
- 发布状态只能由服务端 `PublicationService` 基于权威上下文改变。

Round 00 只交付结构和契约，不自行实现真实业务模块。

## 结果

正向结果：

- API、Worker 与契约可以在一个仓库内原子演进；
- 本地一条 Compose 命令即可运行，便于纵向切片和回滚；
- 模块边界明确，为未来按真实负载拆分服务保留空间。

代价与约束：

- 必须通过代码评审和测试防止跨模块表访问；
- 单体发布仍会同时影响多个模块，需要严格门禁；
- 只有出现独立扩缩容、隔离或发布节奏的证据后，才评估服务拆分。

## 否决方案

- 微服务、Kafka、Kubernetes：首期复杂度与收益不匹配；
- Redis 作为业务事实源：无法满足权威性和审计要求；
- API 与 Worker 复制规则：会产生发布门禁和证据规则漂移。
