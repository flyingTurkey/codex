## CAPABILITY｜二阶段能力目标

平台首先面向四川路桥内部 OIDC/SSO 用户，把多来源文档转化为有证据、可纠正、可撤回、可检索和可订阅的工程行业事件情报。二阶段先在公路、桥梁、隧道、铁路及轨道交通领域证明 20 个真实来源可稳定运营，再通过 50、100、150 来源门禁逐级扩展。事件是信息流和详情页的唯一稳定身份，文档只作为来源与证据；人工处理高风险和异常，普通低风险内容在服务端门禁通过后自动处理。

## CONSTRAINTS｜已确认且不得自行改变的决策

1. 首期仅企业内部访问，不建设匿名互联网访问；继续采用 OIDC/SSO，本地身份只用于明确标记的开发、演示和测试环境。
2. R3 内容在人工审核前只向内部普通用户投影官方标题、内容类型、官方来源、原文发布时间、首次发现时间、原文链接和醒目的“待审核”；关键事实必须为空，且不得进入精选、日报、推荐或通知。R4 只进入隔离区。
3. Event 是唯一信息流和详情身份。Document 只作为来源与证据；不建设跨多轮的 `PROVISIONAL_EVENT` 公开模型。
4. 旧 Item 进入有期限的只读兼容层，保存不可变 `item_id → event_id` 映射；页面使用 `308` 跳转，API 返回弃用信息，不再扩展 Item 业务能力。
5. 只有内容哈希、规范编号、DOI、明确官方更新关系等确定性身份可以自动归并；模糊匹配和模型判断只生成候选，自动放权必须按内容域和关系类型分别通过人工金标、影子运行和回滚验证。
6. 来源按 `20 → 50 → 100 → 150` 四级门禁扩展。3 个月达到 150 来源只是计划目标，不得覆盖质量、合规、成本或人工运营门禁。
7. 首批 20 来源聚焦公路、桥梁、隧道、铁路及轨道交通，并辅以国家级综合安全、标准和通用数字技术来源；达到 50 来源门禁后才扩展其他工程行业。
8. 取消“候选来源池 ≥1000”硬指标，改用覆盖缺口、合格候选、试运行晋级率、淘汰原因和单来源维护成本。
9. 北极星指标是同一版本化人工金标事件集合上的端到端有效情报可用率；各环节比例只用于诊断，不得相乘后冒充北极星指标。
10. AI 观察在 20 来源事件与证据门禁通过后才进入正式信息流；之前只展示题录和由 accepted claims 生成的事实摘要。
11. 邮件和企业微信在 50 来源门禁通过后才启用；此前只提供站内信息流和日报预览。
12. 首期不默认保存服务端浏览历史；只保存实现收藏、订阅、主动下载所必需的数据。浏览历史以后必须显式 opt-in、可清除且有限保留。
13. 不实现多租户，不给所有表预埋 `tenant_id`；使用角色、数据分类、服务边界和发布投影隔离权限。
14. 每轮只修改实现本轮用户价值所必需的技术层；不得为了形式上的“纵向切片”强制制造迁移、Worker 或页面。
15. 金标由业务领域人员负责；关键安全样本双人独立标注并仲裁。开发者和模型不得既生成标签又用同一标签证明自己达标。
16. 金标数量按 20、50、100、150 来源阶段和统计置信设计；R3/R4、纠正、撤回、事故关系等稀有高风险样本定向补充或全量复核。
17. 不新增表示题录的 R0。必须拆分 `publication_risk_tier`、`content_severity` 和 `projection_level`；高风险内容可使用 `METADATA_ONLY` 投影，但风险等级不得降低。
18. 不使用笼统 `source_trust_score`。分别保存并解释来源权威和来源独立性；事实置信度由具体证据、冲突和审核状态决定。
19. 普通用户接口只能读取专用、版本化发布投影及其只读数据库角色；不得直接查询业务表后依赖 `WHERE published=true` 过滤。
20. 连接器配置只能是受版本化 JSON Schema 约束的声明式配置；禁止管理员配置任意 Python、JavaScript、Shell、模板表达式或动态网络目标。特殊站点必须通过代码评审交付适配器。
21. 重点来源 15 分钟目标只适用于明确允许高频访问且具备 API、RSS、Sitemap 或可靠条件请求的来源；其他来源采用来源级合规 SLO。
22. PostgreSQL 是调度事实源；Celery Beat 只周期唤醒调度器，执行任务只携带 `source_id/run_id`。Redis 只负责队列传输、锁和缓存。
23. 正式环境未配置月度模型预算、单任务上限和告警责任人时，默认关闭付费模型调用。
24. 20 来源阶段默认关闭语义搜索；真实搜索金标证明向量召回有增量价值且不破坏精确结果后才允许启用。
25. 失败任务只保存数据库权威输入引用、处理版本、错误分类和幂等键；不得把正文、模型输入或敏感 Payload 复制到日志、Redis 或失败队列。
26. 普通用户只下载平台生成的事件卡、题录、accepted-claims 摘要、证据引用、日报和来源清单；第三方原始全文只有在来源策略记录明确再分发授权时才可提供。
27. 原始证据“不可变”表示保留期内不得覆盖，不代表永久保存；到期删除或加密擦除后仍保留必要哈希、元数据、删除原因和审计记录，法律保全单独冻结。

## IMPLEMENTATION CONTRACT｜跨轮不变量

- 复用现有模块化单体、`PublicationService`、`SourceAdapter`、`AppShell`、`IntelligenceFeedPage`、`TimelineFeed`、`IntelligenceCard`、证据组件和统一契约；不得创建平行发布服务、信息流、卡片或第二套业务数据库。
- PostgreSQL 是唯一业务事实源；原始响应先保存再解析，解析或模型失败不得破坏已有原始证据和已发布版本。
- 所有用户可见事实、摘要、推荐理由和类型字段必须来自 accepted claims，并保持到证据的双向引用。
- 所有外部 I/O 有明确超时、有限重试、退避、速率限制、允许域和 SSRF 防护；网页、PDF、附件和模型输出均为不可信输入。
- API、Worker、脚本、迁移和后台按钮不得直接改变发布状态；所有发布、修订、纠正、撤回和重发必须经过唯一 `PublicationService`。
- 新数据库变更只通过 Alembic，必须验证正向执行和明确回滚策略；不得用生产自动建表。
- 每轮开始记录已有脏工作树；不得暂存、回滚、删除、覆盖或提交进入本轮前的无关用户改动。
- 每轮使用测试驱动：先增加失败测试和契约，再做最小实现，再运行专项和全局门禁。
- 每轮更新 `CHANGELOG.md` 和独立验收记录，提交范围只包含本轮授权变更；真实外部状态不足时必须报告 `BLOCKED`，不得伪造来源、连续天数、金标、截图、模型费用或生产凭据。

## NON-GOALS｜二阶段不做

- 不开放匿名互联网访问，不处理公网备案、SEO、公众增长或广告商业化。
- 不建设全量法规库、工法库、招投标库或原生 App。
- 不绕过登录、验证码、付费墙、robots、访问控制或版权授权。
- 不引入 Kafka、Kubernetes、图数据库、OpenSearch 或大规模微服务，除非后续容量证据和独立 ADR 明确授权。
- 不让模型决定来源准入、事故责任、法规效力、审核结论或发布状态。
- 不用来源数、文章数、摘要数、PV 或候选网址数替代有效情报价值。

## 全轮测试、迁移和 Git 执行规则

1. 仓库现有 `quality-gate` 只聚合 lint、typecheck、test、contract-test、security-check；涉及采集或内容仍要单独运行 `fixture-replay`，涉及前端仍要单独运行 `web-e2e` 和 `web-a11y`。
2. 仓库当前没有第12轮以后的专项 Make target。实现轮必须先检查；若不存在，应把本轮 `phase2-roundNN-test` 加入 `.PHONY`，复用现有 UV、pnpm、Compose和隔离资源约定。需要真实网络、真人、真实渠道或连续窗口的评测放入单独 `phase2-roundNN-eval`，不得加入普通 PR CI。
3. `phase2-roundNN-test` 必须确定性通过才能形成工程提交；`phase2-roundNN-eval` 缺少真实前置时必须非零并使阶段结论为 BLOCKED，不得用Mock或Fixture让它变绿。
4. 凡确需数据库变化，必须先写迁移/约束/权限失败测试，只使用Alembic，并新增对应迁移验证器；扩展现有隔离集成脚本的verifier allowlist时必须继续拒绝非回环地址和非临时测试库。
5. 迁移至少验证“父revision → 本轮head → 父revision → 本轮head”；代表性旧数据需要验证回填幂等、计数、引用和约束。破坏性downgrade会丢事实时，实验室测试必须证明有数据时拒绝，而生产回滚采用回退应用、停止新写入并保留新增事实表。
6. 大回填采用版本化、幂等、可断点恢复任务；Alembic只做有界结构扩展。若本轮不需要数据库变化，明确写“本轮无Alembic迁移”，不得为了形式制造迁移。
7. 每轮开工记录 `git status --short --branch`、`git diff --name-status`、`git diff --cached --name-status` 和 `git log -1 --oneline`。第12轮起若工作树不干净且无法确认归属，立即停止。
8. 禁止 `git stash`、`git reset`、`git checkout --`、`git clean`、`git add .` 和 `git add -A`；只用显式路径暂存，提交前检查完整cached diff。不得amend、rebase或强推。
9. 每轮最终运行适用的专项target、全部全局门禁、`git diff --check`，并在测试后执行安全的环境清理。任一工程必过命令失败，本轮结论必须为未完成。
10. 真实阶段评测未通过时，可以在用户指令明确允许的范围内提交已验证工程工具，但验收必须写阶段BLOCKED，且不得开始依赖该阶段的下一轮。
